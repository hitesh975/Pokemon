# Pokemon Battle RPG Handbook

This handbook is a guide to what is actually in this repository today: how its pieces fit together, how to build and run the current checks, and where to start when changing something. The project is under active development, so some source files describe planned features that are not yet part of the executable.

## What this project is

Pokemon Battle RPG is a C++20 project for a turn-based creature-battling game. The repository currently contains:

- JSON datasets for species and moves, plus code that parses those datasets.
- Data structures for species, moves, stats, and individual Pokemon.
- A stat calculator with a small set of natures.
- A few standalone test programs.

It is **not yet a playable battle game**. The current application entry point returns immediately, and battle turns, menus, and the complete Pokemon-generation flow have not been implemented.

## How the code fits together

### Data types

- `Stats` stores HP, Attack, Defense, Special Attack, Special Defense, and Speed as integers.
- `PokemonType` and `MoveCategory` are enums. The JSON loaders convert strings into these enum values.
- `Move` contains an ID, display name, category, type, power, accuracy, PP, effect text, and effect chance.
- `PokemonSpecies` contains a species ID/name, one or more types, base stats, and level-based learnable moves.
- `Pokemon` in `randomPokemonGenerator.h` represents an individual creature: species ID, level, experience, friendship, nature, IVs, EVs, and four move slots.

### Loading game data

`loadPokemonSpeciesFromJson()` reads `dataset/pokemons.JSON` (it also tries the lowercase `.json` spelling) and returns a map keyed by species ID. Each species entry needs:

- `id` and `name` strings.
- A `types` array containing recognized type names.
- A `baseStats` object with all six integer stats.
- A `learnableMoves` array of `{ "level": integer, "moveID": string }` entries.

Duplicate species IDs are rejected. Parsing, missing-field, invalid-type, and file-open errors are reported as exceptions.

`loadMoves(filePath)` reads the requested path first, then tries `dataset/moves.JSON` and `dataset/moves.json`. The root object has a `moves` array. Each move provides `id`, `name`, `category`, `type`, `power`, `accuracy`, `pp`, `effect`, and `effectChance`. Supported categories in the loader are `DAMAGE`, `PHYSICAL`, `SPECIAL`, `STATUS`, `HEAL`, and `STAT_CHANGE`; `PHYSICAL` and `SPECIAL` both map to `MoveCategory::DAMAGE`.

The paths are relative to the process's current working directory. Run the program or tests from the repository root so the `dataset/` paths resolve.

### GameDataBase

`GameDataBase` is intended as a single access point for loaded species and moves. Its constructor loads both datasets; `getPokemon(id)` and `getMove(id)` return references to stored records and throw `std::runtime_error` when an ID is not found.

The implementation exists, but `GameDataBase` is **not currently included in a CMake target**. Its test source is also not wired into the build. The current executable and configured tests do not use this database yet.

### Stat calculation

`calculateStats(baseStats, ivs, evs, level, nature)` calculates final stats in `src/core/calculateStats.cpp`.

- HP: `((2 * baseHP + HPIV + HPEV / 4) * level) / 100 + level + 10`
- Other stats: `(((2 * baseStat + IV + EV / 4) * level) / 100 + 5) * nature multiplier`, converted to an integer.
- HP is not affected by nature.
- Implemented natures are Hardy (neutral), Adamant (Attack up / Special Attack down), Modest (Special Attack up / Attack down), Jolly (Speed up / Special Attack down), and Bold (Defense up / Attack down).

The calculator applies integer division to EVs divided by four and truncates the final non-HP result when converting to `int`. It does not validate level, IV, or EV ranges; callers are responsible for supplying sensible values.

### Pokemon generation and battles

`randomPokemonGenerator.*` sketches the intended individual-Pokemon generation feature. It has code for choosing IVs, a nature, a level, and learnable moves, but the flow is incomplete: the generation method does not yet construct and return a `Pokemon`, the EVs and calculated stats are not populated, and the class is not included in the CMake build. Treat this as work in progress, not a feature available from the program.

`src/app/pokemon.cpp` currently defines a `BattleState` structure and an empty `main()`. There is no battle loop, damage calculation, command-line interface, or playable flow yet.

## Build and run

### Requirements

- A C++20 compiler.
- CMake 3.20 or newer.
- vcpkg, used to provide `nlohmann-json`.

From the repository root, configure CMake with your vcpkg toolchain file. For example, with a vcpkg checkout at `C:\dev\vcpkg` and the MinGW triplet:

```powershell
cmake -S . -B build `
  -DCMAKE_TOOLCHAIN_FILE=C:\dev\vcpkg\scripts\buildsystems\vcpkg.cmake `
  -DVCPKG_TARGET_TRIPLET=x64-mingw-dynamic
cmake --build build
```

Use the triplet appropriate for your compiler and platform (for example, `x64-windows` for a typical MSVC setup). The vcpkg manifest in this repository declares `nlohmann-json`, which CMake requires.

The configured targets are:

- `pokemon` — the current, minimal application executable.
- `test_stats` — builds the stat calculator example.
- `test_pokemons` — exercises loading species data.

On Windows, run the two currently configured test executables from the repository root:

```powershell
.\build\test_stats.exe
.\build\test_pokemons.exe
```

`test_GameDataBase.cpp` is present but is not a configured CMake target, so it will not be built or run by the commands above. CMake also does not currently register tests with CTest.

## Making a change

- **Changing a species or move:** edit the matching JSON file and keep IDs consistent. Species learnable-move IDs should refer to move IDs in `moves.JSON`.
- **Adding a type or category:** update the relevant enum/string conversion in `src/core/moves.h` and keep the JSON spelling consistent.
- **Changing stat behavior:** update `src/core/calculateStats.cpp` and check `src/tests/test_stats.cpp`.
- **Changing JSON parsing:** update the corresponding loader and `src/tests/test_pokemons.cpp`; keep paths relative to the repository root.
- **Working on the database or generator:** first add the relevant source files to a CMake target. The generator needs a complete return path and tests before it can be treated as usable.
- **Implementing gameplay:** the application entry point is `src/app/pokemon.cpp`; it currently has no game loop or user interaction.

## Current limitations to keep in mind

- `pokemon` builds but does not yet start a game.
- The database and random generator source files are not included in the CMake targets.
- The database test source is not registered as a target or CTest test.
- Dataset loading depends on the working directory being the repository root.
- The existing tests are small standalone programs, not a comprehensive rules or gameplay test suite.

These are descriptions of the current repository state, not promises about the final design.
